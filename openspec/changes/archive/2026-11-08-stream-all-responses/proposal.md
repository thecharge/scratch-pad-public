## Why

The user requires (2026-11-02): "migrate all in the api and mcp to streaming instead of normal request/response". Asked what streaming means here, the user chose: every response is a stream. Verified on 2026-11-02 in the repository: `packages/http-adapter/src/respond.ts` answers every capability with one JSON body (`jsonResponse`); the only streaming today is the administrator event stream (`packages/events/src/sse.ts`, `text/event-stream`); the MCP endpoint is served by `createMcpHandler` from `@modelcontextprotocol/server` 2.4.0 (`packages/mcp-adapter/src/app.ts:63`), whose default `responseMode` is `auto` (one JSON body unless the handler emits a related message first); the library also offers `responseMode: 'sse'` (always stream) and `'json'` (never stream, drops progress notifications).

## What Changes

The user's delivery correction on 2026-11-05 requires substantive implementation batches and one complete blocking verification gate at push, with focused checks during development. The immediate batch fixes the assessed SQLite ETag race and omitted package skills in the API image together with the duplicate verification workflow. Mandatory checks and coverage stay blocking.

The user's decisions, 2026-11-02: JSON stays available through the `Accept` header; all of it streams over HTTP/1.1 and newer; streaming does not exclude requests and responses being JSON; HTTP/2 and HTTP/3 are required; the SDK must not fail; Caddy is accepted only if every request goes through it and it is performant, and the same applies to the end-to-end tests, the end-to-end API tests that produce the documentation, the model tests and the MCP model test; nothing is accepted without headers, and this is handled with end-to-end self-documenting tests. The infrastructure is built in the monorepo as code: Podman and compose; the reverse proxy runs as a container; HTTP/3 is tested with a curl container that has HTTP/3; the integration tests and the end-to-end tests run in that stack.

0. Correction by the user, 2026-11-02: "I never said all must go as events, I said streams, like streaming, the Node.js streaming API." This change therefore does not wrap every response in events. A stream is a body that is produced and consumed piece by piece through the Node.js and Web streaming APIs (`ReadableStream`, `Readable`, back-pressure, abort). The `result`, `item`, `page`, `progress` and `done` envelope written earlier in this change was my own invention and is withdrawn; how a list and a long-running operation are shaped as streams is an open decision (see the end).
1. Response negotiation by `Accept`, which is required: `application/json` one JSON document; `text/event-stream` only for event capabilities (item 9); files with their own media type (item 10). Every response is written to the connection through a stream, not buffered, for all 20 operations. Newline-delimited JSON is kept only for streamed request bodies; as a response form it is withdrawn because AIP-158 says a list response "must not be a streaming response" (https://google.aip.dev/158, source S2 in `sources.md`).
2. No request without its headers: a request without `Accept`, with an unsupported `Accept`, with a body but without `Content-Type`, or without the marker that the proxy adds, is refused with an AIP-193 error that names the header. This is the reading of "I would not accept anything without headers"; the user can correct it.
3. Requests: request bodies are read as streams; a chunked upload is accepted, and an operation that takes a collection accepts a newline-delimited JSON stream.
4. Content, as the user directed (2026-11-03: "full Google AIP - all long running ops should be under AIP-151 so pagination stays the same, which means AIP-158"): a single-resource operation answers its JSON document; a list follows AIP-158 (page size, page token, next page token, one page per response); a long-running operation follows AIP-151 (an Operation resource and the Operations service: list, get, delete, cancel, wait; https://google.aip.dev/151, source S1; https://github.com/googleapis/googleapis/blob/master/google/longrunning/operations.proto, source S3). Verified gap: the API has only `operations.get`.
5. MCP, per the MCP specification revision 2026-07-28 that the user pointed to (https://modelcontextprotocol.io/docs/2026-07-28/getting-started/intro, source S13): the Streamable HTTP transport as published (source S5); progress by `notifications/progress` (S8); long-running work by the Tasks extension (S7), mapped to AIP-151; events by `subscriptions/listen` (S6); lists by MCP cursor pagination (S9), mapped to AIP-158. That revision removed protocol sessions, the GET endpoint and `Last-Event-ID` resumability (S4).
6. Failures: a failure found before the capability starts keeps its HTTP status and its AIP-193 JSON body; a failure during an operation is in the operation's `error` field (AIP-151); a failure inside an open event stream ends the stream and the SDK maps it to its typed error.
9. Events (the first two: the administrator stream and, as the user decided on 2026-11-03, the progress of an operation) are a capability kind of their own, with the same three faces as every other capability: an HTTP endpoint (`text/event-stream`), an MCP capability and an MCP tool, all generated from one definition, in OpenAPI, in the SDK, in the skills and in the documentation. Event capabilities are the only place where `text/event-stream` is the form.
10. Media: files are streamed in both directions over the HTTP API (no whole file in memory, ranges for download, a size limit from configuration, a declared and checked media type). For MCP the user pointed to the File Uploads working group (https://modelcontextprotocol.io/community/working-groups/file-uploads, source S11). Verified: it is a charter; SEP-2356 is listed there as a draft, its GitHub pull request is closed and not merged (S12), the wire format it describes is an inline base64 data URI, and the group has not chosen streaming, chunked or presigned upload. The user's decision (2026-11-03): follow the `skill://` shape of the Skills extension (sources S14, S15), where each file is an MCP resource under a URI scheme read with `resources/read`: an asset is a resource, its bytes are streamed from a dedicated URL, at a path on the proxy where the asset sits in a RustFS object store (sources S16, S17, S18) and is downloaded through the reverse proxy; with tests, end-to-end scenarios and generated documentation. No MCP upload face is claimed, since MCP publishes none; upload streams through the API into the object store.
11. Infrastructure as code is strictly typed and per environment (development, production and others), built from reusable packages, and its state and behavior are tested. The user's order of preference: research open source TypeScript tools such as Pulumi, expecting tests and states of the infrastructure; if none fits, custom packages that drive known tools (OpenTofu and Ansible) and make the infrastructure an application of the monorepo. The research, with sources, and the decision are the first task of the infrastructure; neither is assumed here.
12. GitHub workflows are disabled: no workflow runs, and none is extended; the stack is verified locally. Verified on 2026-11-02: `.github/workflows/verify.yml` exists with `workflow_dispatch` only and `if: vars.CI_ENABLED == 'true'`; it is not triggered automatically, and this change disables it.
13. Performance is measured and reported by the tests: the end-to-end and integration runs include a report of latency (p50, p95, p99 and the time to the first byte or element), usage (requests, bytes, memory and CPU of the containers) and performance (throughput), per operation, per response form and per HTTP version, saved as evidence and shown in the generated pages.
14. The 26 main specs hold `## Purpose: TBD` (verified: every file in `openspec/specs` has that line). The purposes are written, and the delta specs of this change are written against the main specs so that archiving expands them.
7. Infrastructure as code in the monorepo (`infra/`), a Pulumi program (tool chosen by the research in `evidence/6.0-infrastructure-research.md`) run against rootless Podman: a Containerfile for the API; Caddy as a container, the only entrance, terminating HTTP/1.1, HTTP/2 and HTTP/3 (TCP and UDP) and forwarding to the API over HTTP/1.1 without buffering; a curl container with HTTP/3 enabled as the test client for every protocol assertion; a runner container that runs the integration tests and the end-to-end tests inside the stack. The API has no published port and sits on a network the runner and the curl container cannot reach, so a request cannot bypass the proxy; the API also refuses any request without the proxy's marker. Images are pinned by digest and built or pulled by the repository tooling; no unverified third-party image is run. A measurement of the proxy against a direct connection (throughput, latency percentiles, time to the first event) is recorded as evidence.
7a. The infrastructure shares the repository's mentality and rules, and this changes how the project is run, developed and tested. One stack is used for development, tests and production: the same Containerfiles, the same images and the same proxy topology, differing only by environment configuration from `packages/config`. The infrastructure is a typed program with one stack per environment, fed by an environment description in the configuration package (nothing generated and committed, so no drift gate; mock unit tests per environment are the state test); it follows the code guidelines (no comments, no address or port literal outside the configuration package, every data shape a Zod schema, images pinned by digest); the scripts that manage the stack are async, have 2x2 cases and 100% coverage; the checks are blocking in the hooks, `verify` and CI. `bun run dev` runs the stack; the integration and end-to-end tiers run in it; the documentation, skills, commands and guides are rewritten to describe it.
8. OpenAPI describes the three response forms, the required headers and the streamed request bodies; the baseline is updated on purpose. The SDK consumes the forms; the console data provider consumes the streams.
9. Every behavior above is covered by end-to-end tests that produce the documentation: each step of each scenario is a documented step with a pass or fail flag, its request headers, the negotiated protocol and what it checked; a failing scenario publishes nothing; a second run leaves the pages identical.
