## Goals / Non-Goals

**Goals:** every API and MCP response is a stream; the contract, SDK, console, documentation and tests agree and are proven by commands run in this change.

**Non-Goals:** changing what the capabilities do; new capabilities; WebSocket transport.

## Decisions (proposals; the user can correct them)

- Required headers (reading of "I would not accept anything without headers"): `Accept` is required and must name a supported form, else the request is refused before the capability runs (400 for a missing header, 406 for an unsupported one); `Content-Type` is required when a body is sent (400 missing, 415 unsupported); the marker header that the proxy adds is required (see Caddy). New error reasons: `ACCEPT_REQUIRED`, `ACCEPT_UNSUPPORTED`, `CONTENT_TYPE_REQUIRED`, `CONTENT_TYPE_UNSUPPORTED`, `PROXY_REQUIRED`, each with an AIP-193 body and each shown in a generated page by an end-to-end scenario (the `error-cases` check enforces this).
- Negotiation: the `Accept` header chooses the response form (`application/json`; `text/event-stream` for event capabilities only); each is written through a `ReadableStream` body, so the adapter buffers nothing and HTTP/1.1 sends it chunked.
- Request streaming: the HTTP adapter reads the request body as a stream. Collection inputs accept `application/x-ndjson` validated line by line against the same Zod schema; a single JSON body still works (a chunked JSON upload was received in the probe).
- Stream, not events (user correction, 2026-11-02): the body is a Node.js and Web stream. JSON is one document written through a stream; there is no `result`/`item`/`page`/`progress`/`done` envelope. Lists follow AIP-158 and operations AIP-151, as the user directed; both AIPs say the response "must not be a streaming response" (sources S1, S2 in `sources.md`), so a list is one page document and an operation is an Operation document, written to the connection through a stream without adapter buffering. NDJSON as a response form is withdrawn; it stays for streamed request bodies. The user accepted this reading (2026-11-03) on condition that it is tested and validated: tests assert early first bytes over every HTTP version and that the assembled body validates as one page or Operation, and a conformance check fails if a list declares a stream or a newline-delimited response.
- Event capabilities: a capability kind (`kind: "event"`) beside the existing kinds. One definition yields the HTTP endpoint (`text/event-stream`, `Last-Event-ID` resume, keep-alive), the MCP capability (`subscriptions/listen`, source S6; MCP 2026-07-28 has no `Last-Event-ID` resume, source S4) and the MCP tool (a bounded read of the events), the OpenAPI entry, the SDK method (async iterable), the skill text and the documentation. The existing administrator stream at `EndpointPath.Events` becomes the first event capability and the progress of an operation the second (user's choice, 2026-11-03). Event names and payloads are per capability and defined by its schema.
- Media capabilities: upload and download as streams. Download: `Content-Type` and `Content-Length` from the stored object, `Accept-Ranges` and `Range` support (206), back-pressure, abort on client close. Upload: `multipart/form-data` or raw body streamed to the store without buffering, size limit and media-type allow-list from `packages/config`, checksum header verified, partial upload removed. Assets (user's decision, 2026-11-03): stored in RustFS (S16-S18) in the stack on the backend network; downloaded through Caddy at a dedicated URL, the API process not carrying the bytes; MCP follows the `skill://` shape (S14, S15): an asset is a resource under an asset scheme, `resources/list` pages them, `resources/read` returns metadata and a `resource_link` (S10) to the download URL; no MCP upload face (S11, S12 show no published wire format). Upload streams through the API into RustFS by S3 multipart. Presigned URLs, range reads and multipart are RustFS's own documented claims (S17) and are proven by a run before use. Decided by the user (2026-11-03): scheme `asset://`; the download URL is a path on the proxy; authorization is a token checked at the proxy; the size limit is 20 MB (config value). The limit is stored in bytes with MB read as 10^6 (20,000,000). The token-check mechanism at Caddy is deferred by the user to a later authentication change and is not part of this one. The RustFS image is pinned by digest and vetted before it is run. The OpenAPI document describes `application/octet-stream` and multipart bodies; the SDK exposes `ReadableStream` in and out.
- Errors: a failure before the capability starts keeps its HTTP status and AIP-193 body. A failure after a stream opened cannot change the status; it ends the stream abnormally and the SDK maps that to its typed error. The JSON document form keeps the error status when the failure happens before the first byte.
- Infrastructure tool (decided by the research, `evidence/6.0-infrastructure-research.md`): Pulumi with the Docker provider against the rootless Podman socket. The program is TypeScript on Bun (`runtime: bun`), one stack per environment with its own configuration, the file backend for state (no account), unit tests with mocks under `bun test`. OpenTofu (HCL) met the Podman, test and state requirements but its programs are outside the repository's code rules, so it is only the named fallback. Verified features this stack needs: TCP and UDP on one port, an internal network next to a normal one, a health check, two networks on one container.
- Reporting: every integration and end-to-end run records, per request, latency and first-byte time, bytes, protocol and response form; the runner records memory and CPU of each container from `podman stats`; the report (JSON and a generated page) shows p50/p95/p99, throughput and usage per operation, form and version. Numbers are evidence; limits are set by the user.
- GitHub workflows: disabled. The workflow file is removed, the `workflows` check and its test are changed to assert that no active workflow exists, and the guides say that verification is local.
- MCP: `createMcpHandler(..., { responseMode: "sse" })` is allowed by the transport (S5: JSON or SSE, client supports both); the MCP endpoint follows the MCP rules for headers and errors, not the REST API's `Accept` rules; long operations use `notifications/progress` (S8) and the Tasks extension (S7), mapped to AIP-151. The MCP endpoint is behind the same proxy. The installed `@modelcontextprotocol/ext-tasks` 0.2.2 is in `node_modules` and no package.json names it (`sources.md`); using it is task 5.1.
- Infrastructure as code (`infra/`), a Pulumi program run against rootless Podman: `infra/api/Containerfile` (base `oven/bun` pinned by digest, the built app, no published port), the Caddy container (image pinned by digest; its configuration rendered from the typed environment description: TLS from a test certificate authority created when the stack starts, HTTP/1.1, HTTP/2 and HTTP/3 on TCP and UDP port 8443, `reverse_proxy` to the API over HTTP/1.1 with response flushing on, and the marker header added), `infra/curl-h3/Containerfile` (curl built with HTTP/3 from release sources with pinned checksums, on a base pinned by digest). Networks: `edge` (proxy, runner, curl) and `backend`, an internal network (proxy, API, object store). The runner and the curl container are not on `backend`, so they cannot reach the API; this is the structural proof that every request goes through the proxy, and the marker rule is the second one.
- The stack is started and stopped by repository scripts (`bun run stack:up`, `stack:down`, `dev`) that run the Pulumi CLI, installed by `tools:install` pinned by version and checksum, with the docker provider plugin installed ahead of time. A `stack` step of `verify` runs the mock unit tests of the program, renders the Caddy configuration and validates it with Caddy itself, and checks that every image reference is pinned by digest. A check reports a missing Podman with the install command. Rootless Podman cannot bind ports below 1024 on this machine, so the proxy uses 8443.
- Tests run in the stack: the integration tests and the end-to-end tests (API, SDK, MCP, console, recorder) run in a runner container (the pinned Bun image) on the `edge` network and reach only `https://proxy:8443`; the documentation they write goes to a mounted volume owned by the user (user-namespace mapping to be proven). Protocol assertions use the curl container (`--http1.1`, `--http2`, `--http3-only`, `-w '%{http_version}'`) against the proxy; the SDK and the console use the same proxy origin. Unit tests need no stack.
- One program for development, tests and production: the environment description in `packages/config` (a Zod schema) feeds one Pulumi stack per environment; the stacks differ only by that configuration (development adds source mounts and watch mode to the same images, tests add the runner and the curl container, production uses the same Containerfiles and the same proxy topology with real certificates and no test services). `bun run dev` starts the development stack. No address, port or host appears in an infrastructure file except through the environment description. Nothing is generated and committed, so there is no drift gate; the mock unit tests per environment are the state test.
- Infrastructure follows the code guidelines: the program and the stack scripts are async, take no `Promise.all`, have 2x2 cases and 100% coverage; Containerfiles and the proxy configuration carry no comments (the comment rule is extended to them); the environment description is parsed against a Zod schema before use; the `url-literals`, digest-pin and proxy-validation checks are blocking in the hooks and `verify`; new rows in `DEV_RULES.md` and the rules check list them.
- Documentation and skills are rewritten: a new project skill for the stack and a `/dev:stack` command, and the skills `project-setup-and-verify`, `project-testing`, `project-docs` and the guides (`CLAUDE.md`, `AGENTS.md`, `docs/running-verify.md`, `docs/testing.md`) describe running, developing and testing in the stack; the pages the end-to-end tests generate describe the stack.
- Images: the HTTP/3 curl is built in the repository; a community image is used only if the user names one, and then only pinned by digest. No image is run before it is pinned and vetted.
- Performance: a benchmark through the proxy and directly to the API on the same machine records requests per second, latency percentiles and time to the first event for a stream, and shows that the proxy does not buffer; it is saved as evidence. The limit is set by the user; until then the report states the numbers and makes no claim.
- Documentation from tests: scenarios are written once and run over each form and each HTTP version where the behavior is the same; each documented step shows the request headers, the negotiated protocol (from the client), the events or lines received in order and the checks; no behavior page is written by hand.
- Contract: OpenAPI lists the three response forms, the required headers and the streamed request bodies. The generated SDK reads all three forms, sends the headers, and resolves the typed value; a list is also an async iterable. ## Risks / Trade-offs

- Existing JSON clients keep working through `Accept`; the risk moves to the clients that adopt the streams.
- Streams hide HTTP status for in-run failures; the `error` event and the `done` rule carry that, and the SDK maps it back to its typed error.
- Proxies that buffer responses delay events; the response sets `Cache-Control: no-cache` and a keep-alive comment frame.
- 20 operations, the SDK, the console, about 25 documentation pages and many tests change together; batches keep each step verifiable.

## Task 6.7 orchestration implementation

The checks runner gains explicit stack mode. It mounts the existing local rootless engine socket at its original absolute path and sets the remote client endpoint. This replaces startup's host user-namespace command while keeping failure propagation and the intended container owner.
