## Context

Verified in the repository: the structure check (`tooling/scripts/check-structure.ts`) enforces `sync-api` and `eager-collection` and reports lazy-loading warnings; `check-unit-cases.ts` enforces 2+2 with a shrink-only debt list; `run-coverage.ts` reports coverage and is report-only; `packages/skill-protocol` serves skills only from the capability registry; `.claude/skills` holds four OpenSpec skills and `.claude/commands/opsx` the matching commands.

## Goals / Non-Goals

**Goals:** every requirement in the proposal delivered, each proved by a command run in this change; the repository carries its own knowledge.

**Non-Goals:** new product features; branch coverage (the user chose lines and functions); inventing the public URLs.

## Decisions

- Async check: a function is a function declaration, function expression, arrow function or method in `apps`, `packages` and `tooling` product source (not in `testing/`). It must be `async` or have a declared `Promise` return type, or be listed in a tool-config ignore file with a reason. Callbacks passed to synchronous library APIs are the expected ignore entries and are listed for the user's review. This is a reading of "every function"; the user can correct it.
- Skill packages: a configured list of skill directories; each skill is validated against the Skills extension format (`SKILL.md`, frontmatter `name` equals directory name, `description` present), served next to registry skills, filtered by policy.
- Repository knowledge: `CLAUDE.md` is the entry point; `AGENTS.md` carries the same facts for agents that read that name. Both are written from the repository's contents. A check fails if either is missing or does not mention every rule in `DEV_RULES.md`.
- Project skills: one skill per area, each declaring the paths it covers in a mapping file; a self-update skill reads the mapping, finds the skills for changed paths and updates them; a pre-commit job fails a commit that changes covered paths without changing the matching skill or command.
- Util entry points and no cycle (task 7.4): before, `@platform/util` imported `concurrencyLimit` from `@platform/config`, so `config` could not use the util and `load.ts` and the console live provider used sequential loops. Now `@platform/util` depends only on `constants` and `types`: the default limit (`DEFAULT_CONCURRENCY_LIMIT`, 8) lives in `constants`, the `CONCURRENCY_LIMIT` variable is declared in the config schema in `types`, and `concurrencyLimit` (the only reader of `process.env`) moved into the util behind the main entry. The entry `@platform/util/browser` exports `all` without it. `config` and the console import `@platform/util/browser`, so the dependency runs one way (`config` to `util`) and the console bundle holds no `process.env`. Reason for not letting `util/browser` read the variable: a browser bundle has no environment, and the limit for the browser is the default or an argument. The parallelism the two files had before the loop rewrite (`Promise.all` over the issues and over the events of one chunk) is restored, now capped at 8. `check-package-graph.ts` fails on a package cycle and on a console bundle that holds the config loader, the util environment entry or `process.env`.
- Docs site before the browser check (task 7.5): the end-to-end test `ui-docs.test.ts` browses `apps/docs/dist`, which only the later `docs` step built, so a clean checkout failed it (`ENOENT ... apps/docs/dist`). `runDocsE2e` now calls `ensureDocsDist`, which runs the site build (`astro build`, the committed pages) when `apps/docs/dist/index.html` is missing, with `NODE_ENV=production`: under `bun test` the variable is `test`, and a site built that way has no working search box (shown by a run from a fresh worktree where the page test timed out waiting for the search input). The step order of `verify` stays; the test no longer depends on it.
- Cause of the flaky `console-request-log` (task 7.6): the console runs Refine with `liveMode: "auto"`, which refetches the active list on every event of the live stream. Reading the log is itself a request, so the API publishes a `logs.list` event for it, the stream delivers it, Refine refetches, and the next read publishes the next event. Recorded under CPU stress: the same `/v1/logs?capability=books.get` request 28 times in 1.5 seconds with no user action, and after the stack stopped every retry ended in `ERR_CONNECTION_REFUSED`, which the runner counts as a page error (the failing verify run had 9425 of them). The loop only starts when the stream and a read overlap, so it appeared on a loaded machine only. The live provider now drops the events of the console's own reads (`CONSOLE_OWN_READS`: `logs.list` and `stats.get`), so a read cannot trigger the next read. No retry and no change to the runner.
- Process: agents are used one at a time and only for a recorded task; every task is ticked only after the proving command was seen.

## Risks / Trade-offs

- Converting every function to async changes call sites across the whole codebase and may slow hot paths; the ignore list absorbs functions that cannot be async.
- The staleness hook can be noisy; the path mapping is kept narrow and reviewable.
