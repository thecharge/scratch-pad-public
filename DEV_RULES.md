# Development rules

Every rule below is enforced by a **blocking** check in the commit or push hooks (`lefthook.yml`) and in `bun run verify`. Pre-commit keeps staged checks; pre-push invokes the complete verification pipeline once. Documentation builds and knowledge-base recording run at push, with documentation generated and browser-checked by the end-to-end phase. A rule without a blocking delivery check is not accepted. The registry that maps rules to jobs is `RULE_JOBS` in `packages/constants/src/tooling.ts`, and `tooling/scripts/check-rules.ts` accepts a missing individual job only when the canonical full push gate covers it. Commit messages and comment cleanup still require their own jobs.

## How to comply

OpenSpec main specs must have a non-empty Purpose without a TBD placeholder. Active delta targets must apply to the current main specs: MODIFIED and REMOVED headings exist, ADDED headings are absent, and RENAMED sources exist with unused destinations. The blocking `openspec` job in pre-commit and verification runs `check-openspec.ts`; archived changes are excluded.

| Rule                                                              | Enforced by    |
| ----------------------------------------------------------------- | -------------- |
| Meaningful main-spec purposes and applicable active delta targets | `openspec` job |

- **A closed set of strings** is an `enum` in `packages/constants`.
- **A data shape** is a Zod schema in `packages/types`; import the inferred type.
- **A contract with methods** is an interface in `packages/types/src/contracts`.
- **Text for people** is a `MessageId` in constants and an entry in `packages/messages`.
- **Environment variable names** are in `EnvVar`; only `packages/config` reads the environment.
- **A function getting deep** is split into small functions; prefer `map`, `filter`, `flatMap`.
- **A test with several inputs** is one `test.each` table.
- **A test** goes in the folder of its tier under `testing/`; see [testing](docs/testing.md).
- **A unit test** is `unit(subject, { positive: [...], negative: [...] })` with cases from `positive`, `negative` and `rejected`.

## Async, lazy and bounded

- **I/O is asynchronous.** `node:fs/promises`, `Bun.file(...).text()`, `Bun.spawn`; never `readFileSync`, `existsSync`, `Bun.spawnSync` or any other `*Sync` call.
- **State that outlives a call lives in `@platform/store`.** `BoundedStore` has a mandatory `maxEntries`, optional time to live, least-recently-used eviction and an atomic `update`. Caches, rate limit windows, idempotency records and operations all use it, so nothing grows without limit.
- **Collections built inside a function are fine.** A `Set` used to deduplicate one result is garbage once the function returns. The rule only targets collections that live as long as the process.
- **Load on first use.** Capabilities register a loader (`registry.register(id, () => import("./books/get.ts"))`); `lazy(factory)` runs a factory once, on first use. Nothing heavy is imported at startup.
- **Parallel work is capped.** `all(tasks, limit?)` from `@platform/util` runs at most `limit` tasks at once, keeps the order of the list and stops starting tasks after the first failure. The limit comes from `concurrencyLimit` in `@platform/util`: the `CONCURRENCY_LIMIT` variable, or 8. Browser code and `@platform/config` import `all` from `@platform/util/browser`, which never reads the environment. `Promise.all` is not used.
- **Constant lookup tables are arrays or enums,** checked with `includes`, not module-level Sets.

## Comments

There are none. Names, types and small functions explain the code; a comment is bloat, not a fix for unclear code. When a tool must be told to look away, the exception goes into the tool configuration (`overrides` and `includes` in `biome.json`, `ignorePaths` or `words` in `cspell.json`, `project-words.txt`), where it is reviewed as configuration. Documentation belongs in READMEs and the OpenSpec change. `tooling/scripts/strip-comments.ts` removes comments from staged files of every type the repository holds (TypeScript, TSX, YAML, TOML, Markdown, MDX, HTML, JSON, CSS, Grit, `.gitignore`, `.env.example`, `CODEOWNERS`) in the `comments` job, dprint removes them from the types it does not own through its `exec` plugin (dprint itself only formats comments, it cannot remove them), and the `structure` check rejects any that remain, including `biome-ignore`, `cspell:` and `@ts-expect-error` directives.

## Lazy loading warnings

Functions and invocations are lazy: a call at module level (`const x = build()`) is reported as `eager-invocation`, and a static import of a heavy module (`HEAVY_MODULES` in constants) as `heavy-import`. These are warnings, not failures, because modules and imports may be loose. To silence a path, add it to `LAZY_IGNORED_PATHS` in `packages/constants/src/tooling.ts`.

## Suppressions

Biome plugin and rule exceptions are configured per path in `biome.json` (`overrides`, or the plugin `includes` globs). There are no inline suppressions.

The user-authorized alternative `bun run ship:fast` accepts source changes and keeps all static checks, security checks, unit tests and integration tests blocking. Its verification budget is 55 seconds. Normal pushes and `bun run verify` retain full E2E, coverage and documentation production. The fast lane reports its reduced scope and does not claim a fresh full audit.
